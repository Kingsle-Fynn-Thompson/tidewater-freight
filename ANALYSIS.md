Pre-refactor analysis, written before any code was changed. Baseline measured on 19 Nov 2026.

The suite is green but catches almost nothing: 15 of 18 deliberate bugs go unnoticed.

### How the current prices are produced

The formula is spread across the calculator: `rate * weight`, plus a zone fee, plus a heavy surcharge, then an express multiplier.

| Case | Working | Result |
| --- | --- | --- |
| DOMESTIC 10 kg STANDARD | 5 x 10 + 0 | 50.0 |
| REGIONAL 5 kg STANDARD | 8 x 5 + 10 | 50.0 |
| INTERNATIONAL 40 kg EXPRESS | (15 x 40 + 25 + 20) x 1.5 | 967.5 |

The identical 50.0 for DOMESTIC and REGIONAL is a coincidence, not a flat rate. These values will be pinned as characterization tests before refactoring so the refactor cannot change prices by accident.

## 2. Problems in the code

### 2.1 Ranked list

| # | Problem | Where | Principle or smell | Severity |
| --- | --- | --- | --- | --- |
| 1 | Failures swallowed: `catch (Exception e) { return 0; }` | `ShippingCalculator` | Swallowed exception, silent failure | Critical |
| 2 | Unknown service level silently priced as standard | `ShippingCalculator` | Missing validation, stringly-typed input | High |
| 3 | No weight validation (negative, zero, NaN, infinity) | `ShippingCalculator` | Missing validation | High |
| 4 | Zone fees in an `if / else if` chain on strings | `ShippingCalculator` | OCP violation | High |
| 5 | Repository created with `new` inside the class | `ShippingCalculator` | DIP violation, untestable | High |
| 6 | One method does lookup, zone fees, surcharge, express pricing, logging and error policy | `ShippingCalculator` | SRP violation, long method | Medium |
| 7 | Pricing rules split across two places | Repository and calculator | Scattered rule data | Medium |
| 8 | Money as `double`, no rounding | All classes | Primitive obsession, precision risk | Medium |
| 9 | `System.out.println` inside business logic | `ShippingCalculator` | Side effect, SRP | Medium |
| 10 | Magic numbers: 10, 25, 30, 20, 1.5 | `ShippingCalculator` | Magic numbers | Medium |
| 11 | Generic `IllegalArgumentException` for an unknown zone | `InMemoryRateRepository` | Missing domain exception | Low |
| 12 | Demo passes `"MOON"` and gets 0.0, and the label says `STD` while the code passes `STANDARD` | `Demo` | Misleading demo | Low |

### 2.2 Detail

**1. Swallowed failure (the most serious problem).** The repository already does the right thing: for an unknown zone it throws `IllegalArgumentException("Unknown zone: ...")`. The calculator catches that exception and returns `0`. The correct failure is therefore destroyed by the calling code. The catch is also too broad: a `null` zone, a `null` service level, or a genuine bug (a `NullPointerException`) becomes a free shipment as well. The comment in the code ("return zero") shows this was a deliberate shortcut, not an accident, and it is exactly the kind of choice an AI assistant makes to keep output looking tidy.

**2. Unknown service level.** Only the exact string `"EXPRESS"` triggers the multiplier. `"Express"`, `"express"`, `"EXPRES"` or `"OVERNIGHT"` are all charged as standard, silently undercharging the customer's chosen service. Service level should be an enum, with unrecognised input rejected.

**3. Weight is never validated.** A weight of `-5` produces a negative cost (a payout rather than a charge). `0` produces a fee-only price. `NaN` and infinity flow straight through the arithmetic. Nothing rejects them.

**4. Open/closed violation.** Every new zone needs a new `else if` in the middle of the existing logic. Worse, a zone added only to the repository would receive a rate but no zone fee, and nothing would warn anyone: a wrong price that looks valid. The coming new zone would hit this exact trap.

**5. Hard-wired dependency.** `private final RateRepository repository = new InMemoryRateRepository();` means callers and tests cannot supply another repository. The `RateRepository` interface exists but is not used as a seam, so it gives no benefit. This is why the AI-written tests cannot isolate anything.

**6. Single-responsibility violation.** One method performs seven jobs: input handling, rate lookup, zone fee, heavy surcharge, express pricing, console output and error policy. A change to any rule means editing the same method.

**7. Rule data lives in two places.** Base rates (5, 8, 15) are in the repository, but zone fees (0, 10, 25) are in the calculator. Adding a zone means changing both, and nothing enforces that they stay in step.

**8. Money as `double`.** The result is an unrounded `double`. It works for today's values but carries binary floating-point error, and prices are never rounded to a currency precision.

**9 and 10. Console output and magic numbers.** The calculator prints during every calculation, a side effect that pollutes test output and cannot be turned off. The numbers 10, 25, 30, 20 and 1.5 have no names, so a reader cannot tell what business rule each one represents.

### 2.3 Rules that are implicit and need a decision

The code embeds business rules the brief never states. They must be confirmed with the reviewer and then pinned by tests:

- The heavy surcharge applies only when weight is **strictly greater than** 30 kg. Exactly 30 kg is not heavy.
- The heavy surcharge is added **before** the express multiplier, so express also multiplies the surcharge (as the 967.5 result shows).
- Weight of exactly 0 is currently accepted. Should it be?
- Is there a maximum weight?

## 3. Problems in the tests

All three tests are hollow. None would fail if the pricing logic were wrong.

| Test | What it asserts | Why it proves nothing | Verdict |
| --- | --- | --- | --- |
| `calculatesACost` | `cost > 0` for DOMESTIC 10 kg | Passes for 50, for 0.01, or for 5,000,000. A wrong rate, a wrong fee or a broken multiplier all still pass. | Hollow: replace |
| `calculatesExpressCost` | A **mock** of `ShippingCalculator` returns 967.5 when told to return 967.5 | The class under test is mocked, so no production code runs. It would pass if the calculator were deleted. It tests Mockito, not the service. | Worst: delete |
| `returnsACostForAShipment` | `assertNotNull(cost)` on a primitive `double` | A primitive is boxed and can never be null, so this assertion can never fail. It is a tautology. | Hollow: delete |

## 4. Most serious problem, and why

**The swallowed failure (`catch ... return 0`) is the most serious problem in this code.**

- It is the only problem that produces a **wrong business outcome**: a shipment to an unknown zone is quoted at zero, with no error and no log. The customer is undercharged and nobody finds out.
- It is **invisible**. A wrong rate looks wrong; a zero returned inside a try/catch looks like a valid result to every caller.
- It **masks every other failure**, including genuine bugs, so it makes all other problems harder to detect.
- It actively **overrides correct behaviour**: the repository already throws the right exception.

The second most serious problem is the hollow test suite. It is why problem 1 shipped: three green tests, and none of them tries an unknown zone. A suite that reports green over a free-shipping bug is worse than no suite, because it creates false confidence.

The others (hard-wired repository, `if/else` chain, mixed responsibilities) are maintainability costs. They make change slow and risky, but they do not by themselves charge customers the wrong amount.

## 5. How each problem will be addressed

| Problem | Planned fix |
| --- | --- |
| Swallowed failure | Remove the blanket catch. Throw `UnknownZoneException`. Catch only where a cause can be added, and rethrow wrapped. |
| Unknown service level | `ServiceLevel` enum. Reject unknown values with `UnknownServiceLevelException`. |
| Weight validation | `Weight` value object that rejects zero or negative, NaN and infinity at construction (`InvalidWeightException`). |
| `if/else` zone chain | Per-zone data (rate per kg plus flat fee) held with the rate rules, so a new zone is one new entry, not an edit to existing logic. |
| Hard-wired repository | Constructor injection of `RateRepository`. |
| SRP | Calculator only orchestrates. Surcharge and service-level pricing move to small separate policies. |
| Rules in two places | One zone rate object carries both rate and fee. |
| `double` money | `BigDecimal` with an explicit rounding mode. |
| Console output | Removed from the calculator. |
| Magic numbers | Named constants or configuration. |

**Design note, revised from the earlier proposal.** Now that the code is visible, every zone follows the same formula and differs only in its numbers (rate per kg and flat fee). One class per zone would be over-engineering. A data-driven zone rate (a small record held by the repository) lets the new zone be added as data with no code change at all, and only a zone with genuinely different logic would need a new rule class.

## 9. Rationale

### 9.1 What was kept, fixed or rewritten

| Item | Decision | Why |
| --- | --- | --- |
| Rate values (5, 8, 15) and zone fees (0, 10, 25) | **Kept** | These are the business rules. Only their location changed. |
| Heavy-item rule (above 30 kg, add 20) and express multiplier (1.5) | **Kept** | Same rules, now named and injectable. Order of operations is unchanged, which is why `967.50` still comes out. |
| `RateRepository` interface | **Kept, then fixed** | It was the right seam, but the calculator ignored it. It now returns a `ZoneRate` and its contract says an unknown zone throws `UnknownZoneException`. |
| `InMemoryRateRepository` | **Kept as the default implementation, rewritten** | Holds rate and fee together, accepts any map through a second constructor, and makes a defensive copy. |
| `ShippingCalculator` | **Rewritten** | Hard-wired dependency, swallowed failure, `if/else` zone chain, console output and `double` money could not be patched individually without leaving it doing too much. |
| `Demo` | **Kept, updated** | Uses the new API and shows a rejection instead of `0.0`. |
| All 3 AI-generated tests | **Deleted and replaced** | None could fail when the code was wrong (see section 3). Nothing in them was worth salvaging, so keeping them would have been false reassurance. |
| Exceptions, `Weight`, `ServiceLevel`, `ZoneRate`, `HeavyItemSurcharge` | **New** | Each gives one rule exactly one home. |

### 9.2 Key design decisions

- **Each class has one job.** The calculator only orchestrates: look up the rate, add the surcharge, apply the service level, round. Validation lives in `Weight` and `ServiceLevel`, rate data in the repository, the heavy-item rule in `HeavyItemSurcharge`.
- **Dependencies are injected.** The calculator receives its `RateRepository` and `HeavyItemSurcharge` through the constructor. This is what made the Mockito tests possible: a mocked repository can fail on demand.
- **Invalid input cannot exist.** `Weight` rejects null, zero, negative, `NaN` and infinity when it is created, so the calculator never re-checks. `ServiceLevel` is an enum, so a typo is rejected instead of quietly charged as standard.
- **Failures are specific and never swallowed.** The blanket `catch (Exception) { return 0; }` is gone. The only `try/catch` wraps the one external call (the repository lookup). Our own `ShippingException` family passes through unchanged. Any unexpected error is wrapped in `RateUnavailableException` with the original attached as the cause. The exceptions are unchecked so callers are not forced into boilerplate.
- **Money is `BigDecimal`**, rounded to 2 decimal places with HALF\_UP, instead of an unrounded `double`.
- **Zone stays a `String`, not an enum.** An enum would force a code edit for every new zone, which defeats the purpose. The repository decides which zones exist.
- **One class per zone was rejected.** Every zone uses the same formula with different numbers (rate and fee), so separate classes would be over-engineering.

### 9.3 How the design absorbs the new zone

Adding the new zone is one line of data in `InMemoryRateRepository.defaultRates()`, for example `"NEWZONE", ZoneRate.of("20.0", "40")`. The calculator and every existing rule stay untouched. This is demonstrated by the test `aNewZoneCanBeAddedWithoutChangingAnyLogic`.

The old design had a trap: a zone added only to the repository would have received a rate but no zone fee, and nothing would have warned anyone. Rate and fee now live in one `ZoneRate`, so that mistake cannot happen.

Limits, stated plainly:

- If the new zone needs genuinely different logic (for example tiered pricing by weight band), data alone is not enough. At that point a small rate-rule interface should be introduced. It was deliberately not built now, because it would be speculation.
- `Map.of` holds at most 10 entries. That is plenty today, but a larger zone table should use a different map construction.

### 9.4 Behaviour that deliberately changed

- An unknown zone now throws `UnknownZoneException` instead of returning `0.0`.
- An unknown or misspelt service level now throws instead of being charged as standard.
- Weight of zero, negative, `NaN` or infinity is now rejected.
- The calculator returns a `BigDecimal` with two decimals, takes a `Weight` and a `ServiceLevel`, and no longer prints to the console.

### 9.5 What the AI got wrong, and what to look for

The inherited code was built to look finished, not to be correct under failure:

- **It made failure disappear.** A catch-all returning zero turned the repository's correct exception into a free shipment.
- **Its tests could not fail.** One asserted only `cost > 0`. One mocked the class under test and asserted the stub it had just set up. One called `assertNotNull` on a primitive `double`.
- **It hard-wired its dependency**, so nothing could be isolated or made to fail on purpose.
- **It left rules as bare numbers and strings**, with no validation.

What the team can check in future AI-generated code:

1. Search for `catch (Exception` that returns a default value.
2. For every test, ask: if the code were wrong, would this fail? If the answer is no, it is decoration.
3. Be suspicious when the class under test is itself a mock.
4. Run mutation testing, because coverage alone cannot detect any of this (the starter had 61% line coverage).

### 9.6 Improvement beyond the brief: a mutation-testing guard in the build

PIT now runs automatically inside `mvn verify` and fails the build if fewer than 90% of mutants are killed. `Demo` is excluded because it holds no logic.

**Why it adds value for this code.** The failure found in this lab was a suite that was green and caught 17% of bugs. A passing test run cannot detect that, and line coverage cannot either. The threshold turns "are these tests real?" from a one-off review question into a check that runs every time, so quality cannot quietly erode when the next zone or rule is added.

**Limits.** It adds roughly 25 seconds to `verify` (it is not in `test`, so the normal edit-and-test loop stays fast). The 90% threshold leaves headroom for harmless mutants. Excluding `Demo` is a judgement call and is stated here so it can be challenged.

### 9.7 Assumptions awaiting reviewer confirmation

These preserve the original behaviour and are pinned by tests, so they are cheap to change if the answer differs:

1. Exactly 30 kg is not heavy (surcharge only above 30 kg).
2. The express multiplier also applies to the heavy-item surcharge.
3. A weight of zero is invalid.
4. Zone names are case-sensitive (`domestic` is unknown).
5. Money is rounded to 2 decimal places, HALF\_UP.
